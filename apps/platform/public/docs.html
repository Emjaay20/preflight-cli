Product guide · v0.2

Clearance for the build you are actually about to ship.

Preflight is a release-clearance system for Chromium extension teams. It compares a candidate bundle to the last shipped baseline, evaluates versioned policy, and records a human release decision when a build needs one.

01 · Overview

A release decision with evidence attached.

Extension stores and users judge the bundle that was uploaded, not the promise made weeks earlier. Preflight makes that decision legible: it inventories the build, exposes what changed from the baseline, applies policy, and preserves the resulting verdict.

Core rule: automated pipelines may submit and observe a review, but they cannot turn a blocked or review-required build into a release. A reviewer or admin must sign off.
02 · Workflow

From artifact to an accountable decision.

01 · SUBMIT

Bring the bundle

Upload a .zip or .crx with its claims.json, from the Console, CLI, or CI.

02 · REVIEW

Inspect deterministically

Five Rust agents hash, extract evidence, diff the baseline, evaluate policy, and issue a verdict.

03 · DECIDE

Sign off consciously

Clear safe changes, hold unclear ones, or reject the build. The decision is appended to the review record.

03 · Product surfaces

The same review, in the right place for the job.

04 · Policy packs

Rules are versioned, visible, and reproducible.

Preflight ships with a Chromium Web Store pack and a project-claims pack. A review records the selected pack versions so a verdict can be understood later instead of being recreated from a moving checklist.

05 · Sign-off & roles

Automation moves work forward. People own the release decision.

Workspaces use scoped keys and separation of duties. An organization can have multiple isolated projects and baselines; an independent developer gets a personal workspace with the same review workflow.

RoleCan doCannot do
adminManage projects, keys, members, and sign-off.Bypass the recorded decision trail.
reviewerInspect findings and sign off a review.Manage the whole workspace.
ciSubmit builds and read their verdicts.Sign off, hold, or ship a release.
06 · CLI & CI

One key across local review, CI, and the control plane.

# Inspect locally with the same deterministic scanner
preflight review ./build.zip \
  --claims ./claims.json \
  --pack cws-2026.1 \
  --key $PREFLIGHT_KEY

# Push a review record to a workspace project
preflight push ./build.zip \
  --project <PROJECT_ID> \
  --claims ./claims.json \
  --key $PREFLIGHT_KEY \
  --api https://preflight.aetherhost.com.ng

A GitHub Action can upload the real release artifact, wait for the verdict, add it to the workflow summary, and fail a pipeline for block or needs_human. Keep a CI key in the repository’s encrypted secrets; it remains unable to approve a release.

07 · HTTP API

A small API around the release workflow.

POST /v1/signup

Create an individual or organization workspace and initial admin key.

POST /v1/sandbox/evaluate

Run an ephemeral review against public Harbor Node fixtures.

GET /v1/me

Read the active workspace, actor key, projects, and roles.

POST /v1/projects/:id/reviews

Upload a release artifact and optional claims document.

POST /v1/reviews/:id/sign-off

Record a reviewer or admin decision.

POST /v1/members/invite

Invite an organization member with a scoped role.

08 · Trade-offs & limits

What Preflight does well—and what it intentionally does not claim.

Static, not runtime analysis

Preflight does not execute an extension. That limits runtime risk during review and makes scans repeatable, but it cannot prove every behavior that only appears after live configuration, remote data, or user interaction.

Human sign-off adds a gate

Requiring a reviewer for uncertain or blocked builds is slower than automatic promotion. It is deliberate: a policy violation should be understood, not merely acknowledged by a CI token.

Baseline quality matters

A diff is only as meaningful as the last known good baseline. Teams need to establish a cleared first release and keep claims accurate as capabilities evolve.

Policy is explicit, not magical

Versioned rules are auditable and stable. They still need ownership: teams must decide which controls are appropriate and update policy as store guidance changes.
